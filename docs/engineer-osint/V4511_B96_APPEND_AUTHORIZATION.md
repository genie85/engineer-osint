Status: **BLOCKED_PENDING_POST_B96_CI_READINESS**

## Purpose

v4.5.10 installed the fail-safe runtime transition guard and passed production Pages validation while the persistent canonical tip remained `engineer-osint-20260826-B95`. v4.5.11 then pinned the exact reviewed B96 candidate and its expected hashes.

A follow-up review found that the candidate itself is ready, but the current Pages migration-preview chain still assumes persistent B95. A real B96 append at this point would therefore make current-main validation fail after the write. The production append is now explicitly fail-closed until a dual-state post-B96 CI path is installed and validated.

## Current blocker

The existing pre-append chain includes tests and migration-preview scripts whose contracts require the persistent tip to remain B95. Those checks are correct before the append but would become stale immediately after B96 is persisted.

The next code slice must therefore make Pages validation migration-phase aware. It must preserve the current B95 pre-append proof while adding a separate post-B96 path that validates the persisted immutable B96 entry, its exact hashes and scope, then runs the normal current-run build/runtime/media/PUBLIC-CZ/i18n validation against B96. No old preview may be silently treated as a current-state proof.

## Standard helper is now fail-closed

`append-run.mjs --write` contains an explicit B96 authorization guard. Before any B96 file or manifest write it requires:

1. authorization `status=READY_FOR_APPEND`;
2. `post_b96_ci_pipeline_ready=true`;
3. exact run and parent identity;
4. exact parent canonical SHA;
5. exact reviewed candidate file SHA;
6. exact resulting canonical SHA;
7. exactly 104 operations and 15 source appends;
8. single-run scope with no manual manifest/hash edits, B97/B98, overlay retirement or identity-fix migration.

The current policy deliberately fails conditions 1 and 2, so the standard helper cannot persist B96 yet.

## Why the historical `safe_to_append=false` remains unchanged

`V455_STAGE_A_CANDIDATE.json` remains an immutable no-write review artifact. Rewriting it would weaken provenance. A future production authorization is separate and narrow; it may be activated only after post-B96 CI readiness itself has passed review and production validation.

## Scope restrictions after authorization is eventually activated

The eventual production append slice may contain only the single B96 immutable run and its deterministic manifest update produced by the standard append-only helper. It must not include B97, B98, overlay retirement, identity-fix migration, UI/localization changes, schema changes, manual hashes or unrelated cleanup.

After B96 is persistently appended and deployed, all post-B96 current-main validation must pass before B97 is considered. The first three legacy overlays remain active during this step.
